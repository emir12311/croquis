# What Croquis does

The long version of the table in the [README](../README.md). Kept because the detail is
useful — how the breadboard conducts, what the current model does and does not, where a
saved file differs from Wokwi's.

## What works today

- **Desktop app** (Tauri), three dockable columns — resizable, each collapses to a slim icon rail.
- **Code editor** (CodeMirror 6) in the Sketch panel, themed by the app's own tokens. It knows the Arduino API — typing a name offers its **real signature** and `Serial.` lists its members — and **Tab indents** instead of trapping you.
- **Drag components** (Arduino Uno, LED and RGB LED, resistor, pushbutton, rotary and slide potentiometers, photoresistor, NTC temperature sensor and analog joystick, half or full breadboards) onto the canvas — the palette tiles show each part's **real drawing**, not a stand-in icon, and the canvas renders the same `wokwi-elements`.
- **A breadboard that really conducts** — both a half board (30 columns, 400 tie points) and the **full board** (63 columns, 830 points). The five holes in a strip are one net, each power rail is one long net, and the two banks either side of the trench stay separate — so a wire into *any* hole joins the other four in its strip. Components **snap into the holes** when you drop or move them over the board, and a leg standing in a hole is **connected without a wire**, the way it really works. The full board's power rails **break in the middle**, exactly like the real thing — the two halves are separate nets, so bridge them if you want power across the whole board.
- **Wiring, the Wokwi way:** click a pin and the wire follows your cursor; click another pin to connect; click empty space to drop a bend (route a wire around a part); **Esc** cancels. Clicking the **same two pins again removes the wire**. Wires are always **orthogonal**, snap to a fine grid, and draw **above** the parts. Pressing near a pin and *dragging* moves the part instead — which is what lets you grab a breadboard anywhere, rather than only by its edges.
- **Reshape wires** — select a wire to **re-route its endpoints**, **drag its middle** to slide a segment, give it a **colour**, or **Delete** it.
- **Rotate parts** (`R` steps 90°, `Shift+R` turns it 180°) — pins rotate with them.
- **Right-click a part** — an in-app menu (never a native one) with Copy / Cut / Duplicate / Rotate 90° / Rotate 180° / Delete, plus **Edit code** on the Uno, which raises the Sketch panel and puts the caret in it. Right-click a wire to delete it.
- **Zoom, pan, fit, clear** — wheel zooms to the cursor; `−`/`+`/`Ctrl±`/`Ctrl 0`; drag empty canvas to pan; header buttons to fit the circuit or clear the canvas.
- **Undo / redo** (`Ctrl+Z` / `Ctrl+Shift+Z`) over the canvas, plus **copy / cut / paste / duplicate** of parts.
- **Menu bar** — **File / Edit / View / Run**. Until now, undo/redo, cut/copy/paste/duplicate, rotate and delete were keyboard-only; they have a visible home now, each item showing its shortcut. The primary actions deliberately *stay as buttons*: **Run lives in the Circuit bar's top right**, and wiring, zoom and the palette never hide in a menu. The theme lives in **View**.
- **Pin markers on hover** — a marker appears only for the pin under the pointer, on every part (not just breadboards: 400 hole markers read as static).
- **Pin tooltip** — hover a pin and a small label names it: *LED · A · Anode*, *Breadboard · a12 · strip 12 · upper*, *Pushbutton · 1.l*. It says what the element tells us, which is what makes multi-pin parts readable.
- **Editable part properties** — select a part and a **properties strip** under the Circuit bar shows what you can change: an **LED's colour** (7 colours, swatched), a **resistor's value** — typed, in any SI unit from pΩ to TΩ, stored as ohms — and a **potentiometer's position**, a slider with a numeric readout. It's **per part**, not per kind — two LEDs can be different colours — and it round-trips through `diagram.json` (Wokwi stores the same `attrs`), so a 10 kΩ resistor stays a 10 kΩ resistor. What's editable is declared by the catalogue, so a new component brings its own controls.
- **Presets** — **File → Presets** loads a ready-made circuit (**Blink**, **Button**, **Potentiometer**, **Photoresistor**, **Thermometer**, **Slide potentiometer**, **RGB LED**, **Joystick**, **Button + serial**, **Fade**) with its sketch, so you can press Run before writing anything. Each is a real `diagram.json` in the same shape Save writes, so a preset is opened by exactly the code that opens a file — and adding one is a new file in `presets/`, not a code change.
- **Where it differs from Wokwi.** Files are the same format in both directions, with two honest caveats. Wokwi's wire routes support a `"*"` separator that moves the remainder of the route to the *target* pin; we do not implement it, so a Wokwi file using it draws a different path here (the same pins, a different shape). And the extra fields this app adds — `sketch`, and a `title` on the presets — rely on Wokwi **tolerating** unknown fields rather than documenting that it does: real Wokwi files carry an undocumented `dependencies` field without trouble, so it is observed behaviour, not a contract.
- **Dark + light themes**, fully driven by CSS variables (so a config or *matugen* can retheme it).
- **Save / open** the circuit as Wokwi **`diagram.json`** — the same file Wokwi reads and writes, so circuits travel both ways. The sketch rides along in an extra `sketch` field.
- **New** starts a blank circuit without closing the app, and asks first — **Save and start new**, **Discard changes**, or **Cancel** — because the circuit is the one thing here that cannot be regenerated. **Save** writes straight to wherever the circuit lives (no dialog: the picker is for *choosing* a location, not confirming one), **Save as…** is how you move it, and a brief note confirms it landed. A first Save offers your documents folder, not the app's own source tree.
- **Select several parts** by **right-dragging a box** around them, or **Ctrl+A** for everything. The selection can then be **moved, rotated, copied, cut, duplicated, pasted and deleted as a group** — dragging keeps the group's shape, and the right-click menu offers only the actions that apply to *every* part selected.
- **Compile & run** — press **Run**: the sketch is compiled with `avr-gcc` and executed on **simavr**; the Uno's built-in **LED (pin 13) blinks**, and a docked **serial monitor** prints what the sketch sends. Compiler diagnostics are listed with their file and line and **jump to the editor** when clicked. While it runs the **circuit is frozen** (a strip says so, and the palette dims) — the potentiometer's knob and its slider are the one thing that stays live — press **Restart** to apply an edited sketch, or **Stop** to change the wiring. The serial monitor also **sends** what you type to the sketch (`Serial.read()`), with an optional trailing newline. Closing the window with unsaved changes asks **Save and close / Discard and close / Cancel**.
- **Simulated parts** — wired components join the circuit: an **LED** lights when its pin goes high, and a **pushbutton** reads into the sketch (hold it to drive it — it *looks* pressed too). An LED's brightness follows the **PWM duty** of the pin driving it, so `analogWrite` fades it instead of flickering; an **RGB LED** has three independent channels and mixes their brightness. A **joystick** gives two ADC axes and a push-button on SEL. A pushbutton shorts the pin to whichever rail it reaches: to **GND** it reads low while held, to **+5V** it reads high; released, the pin takes whatever else holds it — a pull-down resistor low, otherwise your pull-up high. A **resistor sets the current** it's in series with: 220 Ω gives a healthy ~14 mA, 1 kΩ still lights, 10 kΩ is a bare glow, and **an LED with no resistor is over-driven and reported rather than lit**, the way it would die on a bench. Colour matters too — a blue LED (3 V forward) draws less than a red one (1.8 V). It's a small series model, not a circuit solver: there are no arbitrary parallel networks, and the potentiometer is handled as a fixed divider rather than a general one. **Switch bounce *is* modelled** — a contact chatters for about a millisecond when it changes, so a sketch with no `debounce()` really does see several edges per press, and one with it sees a single clean change. It is a **toggle in the Run menu**, off by default: switch it on to watch an undebounced sketch misread one press.
- **Analogue input** — a **potentiometer** feeds `analogRead`: wire one end to **5V**, the other to **GND**, and the wiper (SIG) to an analog pin, and the sketch reads **value/1023 of the supply in millivolts** — 512 reads ~512 of 1023. Swap the end rails and the track reads the other way round, because that is what you built. **Turn the knob on the canvas while the sketch runs** — the same angle-drag the element itself has — or slide it in the properties strip; the circuit re-solves live, and each drag is one undo step. A potentiometer with an end left floating says so in the properties strip ("Put one end on 5V and the other on GND.") rather than quietly reading nothing; a wiper wired nowhere is left alone. The reference is the Uno's real one — the engine holds AVCC and AREF at 5 V, matching the board they simulate.
- **More analogue sources, one model** — the potentiometer's divider is the template the other analogue parts go through: a **slide potentiometer** (the same track on the element's 0–100 scale, read sideways, swapped ends read reversed like the knob), an **NTC temperature sensor** module (OUT rises across −15…135 °C — hotter reads higher) and a **photoresistor module** (AO sets with its Light slider; DO is its comparator, held high while light passes the Threshold slider). A module's rails are not a bare divider: wired backwards it does nothing and says "Its VCC pin needs 5V and its GND pin needs GND." rather than reading reversed. A powered module lights its **own indicator lamps** — power and comparator — wired or not, and the comparator **drives the pin it's wired to** both ways: below the threshold that pin reads low, not "whatever its pull-up says". All of them solve live from the properties strip and stay lazy about cache re-rasterising (`live` in the catalogue says which parts trim their sprites as they move).
- **Crisp rendering** — the whole circuit is drawn on a `<canvas>` at full device resolution, so it stays sharp even where WebKitGTK would otherwise soften painted DOM (see Development notes).

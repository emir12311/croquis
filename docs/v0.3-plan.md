# v0.3 — the egui rewrite

**Status: planning.** This document is the plan for replacing the current
Svelte + Tauri + WebKit UI with a native Rust/egui application, while keeping the
simulator, the circuit format and the offline/lightweight product constraints.

This is deliberately a *living* plan. It does **not** hardcode the number of
parts, presets, tests, platforms or release dates. Those are measured at each
gate by the inventory tooling described below, and the plan is re-baselined
against that measurement. A phase is finished when its gate passes, not when a
calendar or a checklist written today says so.

---

## 1. Why

The current app is a Svelte UI in a Tauri WebKit window. Its useful core — the
AVR toolchain, simavr bridge, netlist, diagram format and presets — is already
Rust or directly portable to Rust. The webview contributes a large amount of
accidental complexity:

- a DOM/canvas/SVG rendering pipeline, sprite rasterisation and WebKit workarounds;
- an IPC boundary for every compile, pin, timing, serial and input event;
- a second language and toolchain for the domain model;
- WebKitGTK packaging and GPU/driver failure modes;
- a browser-driven test harness for features that are not browser features.

The target is one native Rust application:

```text
eframe/egui window
  ├── croquis-ui      panels, menus, editor, canvas painter, input
  ├── croquis-art     SVG/part drawings -> texture atlas / sprite cache
  ├── croquis-core    document, catalogue, netlist, diagram, presets
  ├── croquis-sim     avr-gcc, simavr, timing, serial, pulses
  └── croquis-app     composition root, file lifecycle, settings
```

The UI must still be **offline**, **lightweight**, **desktop-first** and
**Linux-first**. It must still open and write `diagram.json`, run the same
sketches and behave the same at the circuit level.

### Non-goals for this rewrite

- New part families or a new curriculum. Those can land independently after the
  parity gate.
- Multi-board / multi-sketch support. It should become easier after the rewrite,
  but it is not the reason for it.
- A web/WASM build. The browser target is a separate distribution question.
- A new electrical model. The netlist is ported, not redesigned, until parity is
  proven.

---

## 2. Principles

1. **The old app is the oracle.** Until the cutover gate, `main` remains the
   shipped app. The egui app is developed beside it and compared against it.
2. **No big-bang rewrite.** Every phase is a runnable vertical slice with a
   measurable gate.
3. **The data is the contract.** `diagram.json`, sketch text, pin names and
   project files must round-trip between both apps.
4. **The catalogue is data, not UI code.** Part metadata, pin maps, art assets,
   attributes and behaviour identifiers live in a registry; the UI must not grow
   a branch per part kind.
5. **The inventory is generated.** A script scans the current catalogue,
   presets, netlist behaviours and tests and emits the baseline. Gate thresholds
   are derived from that output, not typed into this document.
6. **Prove behaviour, then appearance.** Electrical and file-format parity come
   before pixel parity. Visual regressions are compared deliberately, not
   assumed.
7. **No runtime network.** No telemetry, no updater, no remote assets. Fonts,
   libraries and part art ship with the app.

---

## 3. The baseline

At the start of the rewrite, the inventory script must record:

- every current part kind, its pins, attributes and editable fields;
- every preset and the diagrams it contains;
- every netlist behaviour and the tests that exercise it;
- every UI feature that has a test, and every feature that only has a manual
  claim;
- current startup time, compile time, simulation throughput, memory and package
  size;
- the current public file format and any tolerated-but-undocumented fields.

The output lives in a generated baseline document (for example
`docs/v0.3-baseline.md`), not in this plan. If the script cannot discover
something, that is a **Phase 0 finding**, not a gap to fill by hand.

The plan uses categories such as “LEDs”, “sensors” and “library-backed parts”
only for orientation. The generated inventory is authoritative.

## 4. Phase 0 — discovery and the three spikes

**Goal:** decide whether the rewrite is viable, and lock the technical choices
that are expensive to reverse.

Run the spikes on throwaway branches/worktrees. Do not delete the current UI.

### 0.1 Inventory and baseline

- Write `tools/inventory` (language and location chosen to match the future
  workspace) that emits a machine-readable catalogue of parts, presets,
  behaviours, tests and file-format fixtures.
- Extract a **parity corpus**: all shipped presets, a set of generated circuits,
  and the sketches that exercise every simulator feature.
- Record performance and package-size baselines.
- Produce `docs/v0.3-baseline.md` from the tool output.

**Exit gate:** the corpus is reproducible; both the current app and a trivial
new binary can consume it; the baseline document is generated, not hand-written.

### 0.2 Spike A — canvas and part art

Prototype in egui:

- draw a large breadboard and a handful of representative parts;
- zoom, pan, rotate and hit-test pins;
- drag, snap and wire two parts;
- load and save a diagram;
- render part art from the chosen source.

Measure input latency, redraw cost, texture memory and startup cost at the
baseline zoom levels.

**Decision:** choose the art pipeline and record why:

- resvg/usvg from licensed SVG assets, with a texture/sprite cache; or
- a hand-drawn painter/vector catalogue for parts where SVG fidelity is not
  viable; or
- a mixed registry where each definition declares its art source.

The decision is per-art-source, not hardcoded per part. The plan does not assume
that every Wokwi element is usable, and the licence audit is part of the spike.

### 0.3 Spike B — editor

Prototype an egui code editor that can:

- edit a multi-hundred-line sketch with syntax highlighting;
- select, copy/paste, undo/redo, find, scroll and handle IME/DPI;
- show a completion list at the cursor (at minimum names/signatures already in
  the Arduino API data);
- jump to a line/column from a compiler diagnostic.

Compare a maintained egui editor crate with a custom `ropely`-style document +
`TextEdit` integration. Do not choose a crate solely by README promises; test
selection, IME and long-line performance.

**Exit gate:** a working editable buffer with a diagnostic jump and a completion
list on the spike; a written decision with measured limitations.

### 0.4 Spike C — engine, files, audio and packaging

Prototype:

- move `engine.rs`/`timing.rs` out of Tauri commands into a plain Rust API;
- compile and run one sketch directly, with batched serial and pin events;
- native file open/save dialogs;
- buzzer audio through a native audio backend;
- a minimal packaged binary on the target distribution(s).

Measure first-run compile time, event latency, audio startup and package size.

**Exit gate:** one vertical "load a preset, run it, hear/see one output, save it"
slice works with no WebKit and no Svelte.

### Gate 0 — go/no-go

- All three spikes have working demos and recorded measurements.
- The art and editor decisions have written trade-offs.
- The parity corpus runs against the old app and at least one new spike.
- A no-go is a valid result: keep the current app and revisit only if the
  blocking risk changes.

## 5. Phase 1 — extract the Rust core

**Goal:** make the circuit domain independent of both UIs.

Deliver crates/modules for:

- document model: instances, wires, ids, attributes, undo snapshots, clipboard;
- catalogue: part definitions, pin grouping, fields, art descriptors;
- netlist: nets, power rails, resistances, analogue sources, drives, outputs,
  display memory and relay contacts;
- diagram format: parse/build, validation, unknown fields;
- presets: embedded/bundled data and same loader path as files;
- geometry/routing: grid, snapping, orthogonal routes (no diagonals);
- behaviour registry: the electrical families, not per-kind UI switches.

Port the existing tests or generate equivalent cases from the parity corpus.
The goal is not “same line count”; it is **same observable results**.

### Gate 1

- The Rust core passes the behavioural corpus with no UI attached.
- Round-trip diagrams from the old app load and save unchanged (apart from
  explicitly documented normalisation).
- A differential runner can compare old and new netlist outputs over the corpus.

---

## 6. Phase 2 — application shell

**Goal:** the native app can be lived in without parts.

Deliver:

- eframe window, panel layout, resizable/collapsible panels, menu bar;
- theme tokens (light/dark, no third theme), fonts bundled;
- new/open/save/save-as, unsaved-close guard, error surface;
- undo/redo, clipboard, keyboard shortcuts, focus handling;
- settings persistence;
- a headless-testable shell.

Translate the current design constraints explicitly: no shadows, no stacked
popups, docked panels, CSS-variable-like tokens, no fake loading states.

### Gate 2

- File lifecycle and shortcuts have automated tests.
- A shell-only build runs on Linux, loads/saves a diagram, and passes the
  packaging smoke test.
- No webview dependency remains in the new binary.

---

## 7. Phase 3 — canvas, catalogue and wiring

**Goal:** a real circuit can be built entirely in the new UI.

Deliver:

- egui canvas with pan/zoom/fit, grid, crisp DPI-aware drawing;
- catalogue registry + palette thumbnails;
- part placement, snap-to-hole, selection, marquee, move, rotate, copy/paste;
- pin hit-testing from registry geometry, not DOM;
- wiring, bends, endpoint moves, colours, wire deletion;
- undo grouping, dirty state;
- sprite/texture cache with explicit memory limits.

Port one **vertical family** first (passive + LED + Uno + breadboard), then grow
the family set from the inventory. Each family adds data and tests; it must not
add a UI branch.

### Gate 3

- The parity corpus's placement/wiring/undo cases produce equivalent documents.
- Tool interaction is covered by deterministic headless UI tests.
- No part is considered “done” until it can be wired, driven, seen and tested.

---

## 8. Phase 4 — editor, compiler and runtime

**Goal:** the loop the app exists for: write, run, observe.

Deliver:

- editor integration from Spike B;
- compile via the extracted toolchain/sim engine;
- diagnostics list with file/line parsing and jump-to-caret;
- serial output, serial input, batching and follow-at-bottom;
- run/stop/restart, frozen-circuit state, pin/duty/timing/analogue events;
- input controls (buttons, knobs, sliders, toggles, keypad/joystick/remote) with
  the same semantics as the current netlist;
- buzzer audio, mute/volume policy, no blocking UI thread.

### Gate 4

- Every runtime feature in the inventory has a parity test or a documented,
  owner-approved exception.
- A representative sketch compiles and runs with the packaged toolchain, not
  just the development tree.
- CPU and memory use stay within the Phase 0 envelope, or the delta is accepted
  explicitly.

---

## 9. Phase 5 — full part and behaviour parity

**Goal:** all supported parts behave, not just a demo subset.

Work from the generated inventory. For each family:

- catalogue entry + art + pin map + fields;
- electrical/behaviour model + warnings;
- interaction (knob, slider, toggle, button, press, drag);
- render state and caching;
- preset(s) and tests.

The number of parts, the order and the presets are **not fixed here**. The
inventory and risk decide the order. High-risk families (stateful protocols,
multiplexed displays, library-backed parts, audio, native input) get spikes
before mass porting.

### Gate 5

- The differential corpus reports no unexplained electrical or file-format
  differences.
- Every preset in the old app loads in the new app and produces the same
  observable state under the same inputs.
- The manually claimed-only features have either a test or an explicit exception
  list.

---

## 10. Phase 6 — visual, accessibility and interaction parity

**Goal:** make it feel like the same product.

- Compare screenshots at deterministic zoom/DPI for every part/family.
- Check light/dark themes, focus rings, contrast, reduced motion.
- Keyboard-only operation for menus/panels/editor/canvas.
- IME, compose, clipboard, drag/drop, HiDPI and multi-monitor.
- Text rendering, font fallback and bundled fonts.
- No animations that can make a driver/UI path regress without a fallback.

### Gate 6

- Visual diffs are reviewed, not merely generated.
- Accessibility and keyboard paths are exercised on a real display server.
- The owner has used the new app for a real session and signed off on the feel.

---

## 11. Phase 7 — packaging and cutover

**Goal:** ship the native app and retire the webview app.

Deliver:

- build/sign/package pipeline for the supported Linux formats;
- install/uninstall, desktop entry, icons, bundled toolchain and libraries;
- a packaged build that compiles **and links** a sketch, loads a preset, runs it
  and saves it;
- upgrade/uninstall tests on a clean machine (or clean container);
- release notes and migration notes;
- deprecate the Tauri/Svelte app only after the parity and packaging gates.

### Cutover rules

- Keep the old app available as the previous release for rollback.
- Do not delete the old UI during the rewrite; archive it only after the cutover
  gate and a release that passes installed-package testing.
- The first egui release may be marked as a transition release; the owner
  decides the version number and channel.

### Gate 7

- Installed packages pass the same end-to-end checks as the development build.
- The old app can be removed from the build without breaking presets, diagrams or
  the release pipeline.
- The owner can install the new artefact and use it.

## 12. Workstreams

These run in parallel where dependencies allow; the phase gates define the
minimum order.

| Workstream | Scope | Main risks |
| --- | --- | --- |
| Core/domain | document, catalogue, netlist, diagram, presets, routing | semantic drift from TS; performance of per-frame solves |
| Simulation | toolchain, simavr bridge, timing, pulses, serial, events | threading, event volume, batching, shutdown |
| Canvas/art | painter, textures, SVG pipeline, pin geometry, hit-testing | art fidelity/licensing, DPI, cache memory |
| Editor | text model, highlighting, completions, diagnostics | IME, performance, undo/selection |
| UX/shell | panels, menus, theme, shortcuts, file lifecycle | native platform differences, accessibility |
| Packaging/QA | eframe backend, deb/rpm/AppImage, crate audit | GPU/driver compatibility, third-party dependencies |
| Migration | parity corpus, differential runner, inventory, docs | false equivalence, missing manual claims |

## 13. Testing strategy

### 13.1 Inventory-driven parity

The inventory script is the source of truth for “what exists”. It produces a
matrix of:

```text
feature -> old implementation -> new implementation -> test -> status
```

A feature without a row is a finding. A feature with no test is a finding. A
feature with a manual-only claim is marked as such until the owner signs it off.

### 13.2 Test layers

1. **Pure core tests** — document, netlist, format, routing, catalogue.
2. **Simulator tests** — compile/link/run, timing, input pulses, serial, shutdown.
3. **Differential tests** — old vs new netlist/format on the same corpus.
4. **Headless UI tests** — deterministic egui frames, pointer/keyboard input and
   state assertions; visual snapshots where stable.
5. **End-to-end tests** — packaged app: load preset, run, interact, save.
6. **Fuzz/property tests** — malformed diagrams, random wire graphs, rapid input.
7. **Performance tests** — startup, load, pan/zoom, run throughput, memory, package
   size, measured against the Phase 0 baseline.

Thresholds are set at the gate from measured baselines. They are not guessed
today and not adjusted silently to make a build pass.

### 13.3 Test data

- The parity corpus is generated from the current app's catalogue and presets,
  plus edge cases recorded when tests fail.
- Every new regression becomes a fixture.
- The old app remains buildable for differential runs until the cutover.

---

## 14. Performance and size budgets

At Phase 0, record baseline numbers for:

- cold start and warm start;
- time to open the largest preset and first frame;
- compile time for a representative sketch;
- simulation event rate and UI redraw rate under a busy sketch;
- memory at idle and under simulation;
- packaged size for each distribution format.

Each later gate compares against that baseline. A regression must be explained
and accepted by the owner; it must not be hidden by a new “target” invented at
the end.

---

## 15. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| SVG art fidelity/licensing | Spike A; per-source decision; licence audit; fallback painter for a family |
| Editor quality (IME, selection, syntax) | Spike B; compare a crate against a custom model; keep the editor isolated |
| Netlist drift during port | Differential corpus; port behaviour before UI; no “cleanup while porting” |
| Event/threading regressions | Direct Rust channels; batching; shutdown tests; parity of event ordering |
| Native audio device differences | Abstract audio; no-op fallback; test with no device; mute policy |
| GPU/window backend regressions | Spike C on target distributions; choose glow/wgpu with a measured fallback |
| Packaging dependency surprises | Package early; test installed artefacts, not just `cargo run` |
| Scope creep from new features | Freeze feature work until the parity gate; new features get their own branches |
| Dual-app maintenance cost | Time-box the rewrite; archive the old UI at cutover; no long-term forks |
| Plan becoming a fixed promise | Re-baseline at every gate; inventory and gate results replace stale assumptions |

---

## 16. Definition of done

The rewrite is done when:

- the native egui app can load every current diagram/preset, build, wire, edit,
  compile, run, interact with and save circuits;
- the old and new netlist agree on the parity corpus, with exceptions explicitly
  listed and approved;
- the installed package passes the end-to-end checks on a clean machine;
- the owner has used it for a real session and accepted the feel;
- the old webview app can be removed without breaking the build, presets,
  diagrams or release process;
- the documentation, release notes and rollback path are updated.

Until then, the old app remains the stable product and the new app is a branch,
not a replacement.
